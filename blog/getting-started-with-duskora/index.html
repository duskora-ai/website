From sign-up to shipped: your first ticket with Duskora

Setting up Duskora takes four steps: sign up, add a model key, connect GitHub and pick a repository. Then you write a ticket and watch agents plan, build, review and test it, while you decide what ships. Here is every screen, recorded in the real app.

Most tools promise you'll be up and running in minutes. We wanted to show it instead. Below is every screen a new team sees, from the sign-up page to a merged pull request, recorded in the real Duskora app.

The short version: you sign up, add a model key, connect GitHub, pick a repository and write a ticket. That's the whole setup. From there, agents take the ticket across the board and stop for your approval before anything ships.

What you need before you start

  • A GitHub account that owns the repository you want agents to work in, or admin access to it.
  • A model API key. Duskora is bring-your-own-key, so model usage is billed by your vendor, not by us. This guide uses Anthropic; OpenAI works the same way.
  • A ticket worth doing. Something small and well defined is ideal for a first run.

1. Start your free trial

Every plan starts with a 7-day free trial and no card is needed. Create an account with your email, or continue with Google.

2. Name your organization

Your organization holds your projects, members and connections. Name it and Duskora creates a Main project with the default flow already set up: Plan → Build → Review → QA → Approval → Deploy. You can change the flow later, but you don't have to.

3. Add your Anthropic key

A welcome screen walks you through the connections. First, pick a model vendor and paste its API key. Duskora checks the key with the vendor before saving it, stores it encrypted, and only ever shows you the last four characters.

4. Connect GitHub

Click Connect GitHub and install the Duskora GitHub App on your account or organization, choosing which repositories it can see. There are no personal access tokens to create or rotate: each agent run gets a short-lived token scoped to the repositories it needs, and the agent's shell never sees it.

Slack, Linear and Jira are optional. Connect Slack to approve changes from a message, or Linear or Jira to pick up tickets from the board you already use. You can skip all three for now.

5. Pick a repository

In the project's settings, choose which repository the agents work in. That's the last piece of setup. Everything else on this page, like how the repo deploys or which files count as infrastructure, has sensible defaults.

6. Write your first ticket

On the board, click New ticket. Write it the way you'd write it for a teammate: what you want and how you'll know it's done. The acceptance criteria matter, because QA tests against each one.

New tickets wait in Backlog. Drag one into Plan and the agents take it from there.

7. Watch it move across the board

Each column is owned by an agent. The ticket moves on by itself as each one finishes, and the board updates live.

  1. PlanReads the ticket and the codebase and writes a step-by-step plan.
  2. BuildImplements the plan on a branch, runs the tests and opens a pull request.
  3. ReviewA separate agent reviews the diff against the plan, and sends it back to Build if it isn't right.
  4. QABuilds the branch, runs the checks and verifies each acceptance criterion with a test.

8. See exactly what the agents did

Open the ticket to see the trail. The plan is right there, so you can check the approach before you read a line of code.

Below it, the activity log shows every run: which agent and model ran, what it cost, and a log of what it did. Here QA reports that all three acceptance criteria are met, and Review has approved the change.

9. Approve, and it ships

Nothing deploys without you. When the agents are done the ticket waits at the approval gate with a link to the pull request. Review it like any other PR, then approve, or send it back to Build with a note saying what needs to change.

After you approve, Duskora rebases the branch, waits for CI, squash-merges the pull request and watches the deploy through to production. If the base branch has moved and there are conflicts, it sends the ticket back through the pipeline rather than guessing.

What just happened

Setup took four steps: a key, a GitHub connection, a repository and a ticket. After that, one ticket went from a few sentences to a merged pull request with a written plan, an independent code review, tested acceptance criteria and a human approval, and every step left a record you can read.

That's the loop Duskora runs for every ticket on your board. Put ten through it during the trial, keep the judgement calls, and let the agents do the legwork.
